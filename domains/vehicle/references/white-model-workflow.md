# 图片 → 图生三维白模 → 结构精修 → 网页车辆配置器

## 输入、路由与产物

用户提供一张或多张车辆图片即可开始。尺寸、零件参数和官方模型是可选增强信息，不要求用户补齐才能启动。已有原图、多视图或 GLB 时复用，不重复生成。本文件适用于已选择图生三维候选的任务，不作为所有图片任务的默认路线。候选 GLB 按 [加工路线](tool-routing.md) 优先用 Three.js／原生 GLB 检查和局部加工；复杂建模按需使用 Blender CLI + Python，不被描述为自动恢复未知实车结构。

集中优化统一按 [model-optimization.md](model-optimization.md) 选择基线、诊断和方法。本文件描述可选候选生成及后处理；已有可用资产时跳过生成，已通过步骤按身份复用。整体比例/窗线/屋顶等不准时先修形，局部表面和材质加工延后；无须每次重走以下全部阶段。

图片不能替代图生三维服务的凭据和可用额度。开始时检查已有直接接口和所选路线工具；没有服务时仍可完成参考图和提交准备，支持导入用户在外部生成的 GLB。需要复杂本地建模时检查 Blender CLI；不把未经验证的基础形体作为高保真替代。创建或升级 Skill 不启动实际付费建模。

每个任务保留原始图片/模型、参考来源、候选原件、白模检查图、问题清单、精修版本、网页 GLB、网页源码及验收记录；使用 Blender 时附精细 .blend，原生加工路线保留脚本/参数和高精 GLB。使用已有 project.json 跟踪状态；相机和修复计划单独保存，不增加与现有脚本不兼容的必填字段。密钥不进入任务报告或网页。

## 1. 参考图准备

- 保留上传原图，确认是哪一辆车、哪套轮毂和外观配置；不能仅凭徽标猜车型后替换掉原图造型。
- 优先使用用户真实提供的正前、正侧、正后、前斜、后斜图。单图不足时生成这些完整车辆视图作为设计参考，分别保存，标注原图或 AI 推断。顶部、玻璃、灯具、轮毂等近景按加工需要增加。
- 核对跨视图的车高/车长比例、窗线、轮距、轮毂、灯形和雷达位置。发生矛盾时修参考或保留不确定项，不能要求一个几何模型满足互相矛盾的图片。
- 多图 API 使用各自独立的图片，遵守该接口支持的角度和张数。拼图用于查看，不直接作为多图输入。AI 补图没有增加隐藏区域的真实证据。

## 2. 白模候选生成与质量门 A

按 providers.md 使用现有 Meshy / Tripo 的 prepare、submit、status、download；实际提交前重新核对官方 API 与当前模型版本。默认纹理关闭，先判断形体。腾讯等网站或外部工具的白模可导入同一后处理流程；没有对应适配器时明确仍需外部生成，不能用文件导入冒充 API 实测。

保留高精度候选原件，不先降到低面数。带纹理候选也可用，但检查副本统一关闭照片纹理、凹凸和发光，使用中性灰白材料。先渲染实际模型的前、侧、后、参考斜角，再为有问题部位增加近景。初次预览可低采样并降噪，以可识别形体和边界为准。

质量门 A：检查轮廓、窗线、轮胎圆度、灯腔、面片棱角、曲面凹坑及部件融合。面数和执行成功不能证明形似；平滑法线只修反光，不修错误轮廓。整体比例严重错误则候选 needs_revision/reject；局部可修则进入有范围的加工计划。第二候选只在质量不足、预算允许且已有授权时生成。

不要报告未经定义与测量的 90%/95% 相似度。需量化时先拟合参考相机，再记录轮廓重叠或关键点误差及测量方法；这些仅代表相应视图，不代表全车真实准确率。

## 3. 分区诊断与关键区域样板

问题清单按区域记录：参考证据、实际模型截图、问题类型（几何/法线/材质/UV/灯光/网页）、严重度、拟采用方法、影响范围和未验证项。先选择最影响品质的区域做样板，例如玻璃与车顶连接；不要一次改整车而失去归因和回退能力。

分清修复方法：

- 轮廓或曲面错误：拟合曲面、局部重建/重拓扑、建立倒角与厚度，再校正法线；不能只提高细分级别或加车漆清漆层。
- 几何可用但材质错分：优先按实际部件分配材质。保留源网格的纹理遮罩只用于确实尚未拆分的区域，不按颜色深浅或单一高度自动决定所有结构。
- 网页看起来与 Blender 不同：检查线性颜色、贴图色彩空间、金属/粗糙度、法线及灯光，使用导出的实际 GLB 校准。

局部重建删除或隔离被替换的旧面，避免重叠闪烁。确认切口是可连接的边界；有凹形、多环或相邻独立表面时分区处理，不能盲目把所有点按投影极角排序后封口。新旧曲面连接需校验真实边界位置和过渡法线；简单坐标吻合不保证没有锯齿、尖刺或反光断层。

记录允许改动的部件与接缝过渡范围。保护相邻玻璃、饰条等部件的几何和材质，不因屋顶投影范围而误切侧窗。接缝范围依据当前模型尺度确定，不复用某辆车的固定坐标或距离。若源模型为单一整体网格，现有部件前缀检查不足以验证局部范围，需额外比较未授权区域的顶点位移，并保留报告。

样板前后采用同一相机和灯光，比较无贴图白模及至少一个能暴露染色边界的明亮/有色车漆。必须实际看图；发现旁边结构变形、漏面或尖刺时继续修复。样板通过只代表该区域，通过后再逐区域扩大，不直接标整车 passed。

## 4. 结构材质与质量门 B

建立当前车型实际需要的角色映射（名称可变，绑定必须精确）：车身车漆、玻璃、密封橡胶、固定深色雷达、金属饰条、前/尾灯透镜与发光、轮毂/轮胎。车顶钣金随车身配置换色；行李架、双色车顶等以当前参考为准，不能推广某张图的颜色为所有车型规则。

- 换色只改变声明为车漆的部分；玻璃、橡胶、雷达和灯具按各自配置保持材质。
- 车漆采用材质反光，去除造成掉漆错觉的固定照片高光；保留正确的细节，不能一律抹掉全部贴图。
- 使用前、后、顶部和近景检查上下窗沿、A 柱、顶棚、雷达和灯腔边界。不要只确认几个代表采样点就认定整条边界完成。
- 验证实际网页换色与灯光控制代码，换色不影响固定材质，灯光开关不影响车顶。Blender 渲染不能替代网页 WebGL 检查。

质量门 B：相关区域白模、结构边界及材质检查都通过；未完成部分仍记 needs_revision。玻璃若为不透明展示材质需说明，不能冒充真实可见座舱。

## 5. 配置资产与程序优化

先保留高精度母版，再单独做网页版本。可按预算制作 LOD、压缩纹理、适度减面与法线烘焙；是否使用 Meshopt/Draco、KTX2 取决于已有工具和加载器支持，不为流程完整安装所有优化依赖。减面前后比较轮廓及玻璃、灯具、轮毂、窄饰条，不能为了减小文件重新破坏已修边界。任何压缩版本都要验证实际解码加载。

材质绑定按真实 GLB 节点/材质清单执行，避免基于名称猜测和整车统一涂色。检查 GLB 文件头、索引、有限坐标、实际三角面、贴图尺寸与资源大小；同步校验网页配置及 HTTP 服务的资源版本。JS 语法与换色单元检查通过，不等于 GPU 编译或交互通过。

开门要求独立门体、铰链轴心、门内侧与可见座舱；换轮毂要求实际成套变体。仅有外观图片时这些是额外资产加工，不能用开口或普通照片伪造。内饰可选择真实三维座舱或固定眼点的 2:1 全景；全景模式禁用平移，旋转时不穿到车外。未具备的功能隐藏。

## 6. 网页实测与质量门 C

在 Three.js 配置器中实测旋转/缩放、全部车色、灯光、启用的轮毂/开门/内饰功能，以及错误状态。至少查看参考角、前后、侧面和顶部；检查窄屏布局。测目标设备首屏、帧率和内存后决定进一步优化，不把桌面离线渲染或文件大小当手机性能证明。

浏览器工具不可用或受安全策略限制时，不绕过限制；保留离线和 HTTP 证据，将浏览器/GPU与设备性能明确列为未验收。可交付诊断样板，但不能标质量门 C passed 或正式全功能验收。

交付本地预览、同相机交互对照、原始模型、所用路线的可编辑资产或可重跑脚本、网页 GLB、源码及验收报告。保留旧版入口或配置回退文件。报告分别列几何、结构材质、功能与性能状态，不能用一项通过覆盖其他未通过项。公网发布单独依照用户授权处理。
